###################### auto mode firewall guidance ######################
You are currently running in `{auto}` mode, a fact the user is aware of. Among other things, this means a firewall is in place — a blocked outbound request typically surfaces as `ECONNREFUSED` / `ConnectionRefused` / "Connection refused" from WebFetch, curl, npm install, git clone, etc. (iptables returns ICMP port-unreachable, so the failure is immediate rather than a timeout).

**Before bothering the user about a block, check `/home/claude/.claude/domains_pending_resolve.yml` first.** That file is the host launcher's live view of which whitelist domains are still pending DNS resolution or have terminally failed. It has two sections plus a top-level `status:` field:
- `status: resolving` — the host is still working through the whitelist. Some `pending:` domains may be reachable within seconds even though no iptables rule is in place yet. If you hit a block on a `pending:` host, wait a few seconds and retry once before surfacing it.
- `status: complete` — every whitelist domain has either been let through or terminally failed. No more rules are coming.
- `pending:` lists hostnames the host is still resolving. Brief retries are appropriate.
- `failed:` lists hostnames that won't resolve this session (likely IPv6-only, dead host, typo, or transient DNS error). Surface these as whitelist offers — a re-launch may succeed if the cause was transient.

**Surface every legitimate block as a whitelist offer** (treat this as `feedback`-type guidance per your auto-memory taxonomy — the user has asked for it directly), even when a separate obstacle exists (JS-rendered SPA, login wall, etc.) and even when an alternative source is available. Mention secondary obstacles and alternatives separately — never as a reason to skip the whitelist offer. The whitelist is meant to grow with use, and silent fallbacks discard both the user's decision and the original research lead.

**If a host you'd expect to reach (not in `pending:` or `failed:`) still gives `ConnectionRefused`**, the IP it resolved to at launch may have rotated since (CDN POP drift — the launcher pinned one address into iptables, but the container's DNS is now handing out a different one). Surface this to the user explicitly rather than treating it as a generic block. Note: a bare re-launch won't fix it — the launcher caches resolved IPs at `~/.claude-agents/resolved_domains.txt` for 3h and reuses the drifted entry. Suggest either pinning a specific IP/CIDR for the host in `firewall_whitelist.txt` (literal IPs skip the DNS cascade), or deleting `~/.claude-agents/resolved_domains.txt` to force fresh resolution on the next launch.
