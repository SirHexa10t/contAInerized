  Three clear tiers emerge:

  Light (~50–150 MB, broadly useful even for non-artists): ffmpeg, ImageMagick, graphviz. A research agent converting PDF figures or an architect agent rendering dependency graphs benefits from all three.
  Medium (~200–600 MB, artist-specific): Inkscape, plantuml (pulls in JRE), librsvg, OpenSCAD, mermaid-cli (pulls in Node).
  Heavy (600 MB–2 GB+ each, deserves isolation): Blender, full TeX, Stable Diffusion stacks. Each represents a meaningful decision, not a casual add.


  Architectural implication
  This is exactly the condition your TODO's revisit rule names — "a specific domain genuinely needs a heavyweight system tool that shouldn't live in every image." An artist agent, especially a 3D one, is the strongest realistic trigger for activating the multi-stage split. Three shapes it could take:

  1. Single art target (FROM base AS art): ImageMagick + ffmpeg + Inkscape + graphviz in one stage. ~500 MB extra. Good if you want one generalist visual agent.
  2. Tiered targets: art-2d (image/vector/diagram), art-3d (+ Blender + OpenSCAD), art-doc (+ TeX). Only worth it if you end up with several specialized artist agents.
  3. Cache bind for tool state: whichever target you use, add mounts for ~/.config/blender/ and ~/.cache/blender/ (and TeX's ~/.texlive/ if relevant) — same pattern as your CACHE_HOME, so add-ons, fonts, and render caches survive image refreshes.


  Practical suggestion

  If an artist agent isn't imminent, no action — your TODO's "revisit if (c)" will trigger cleanly when the time comes. If it is imminent, I'd commit to a two-target split (base + art) rather than three; smaller jump, easy to subdivide later.

  One adjacent thought worth flagging: ffmpeg + ImageMagick in the base image might earn their place even without an artist agent. Both come up for research and documentation work (PDF → image, video frame extraction, image optimization for READMEs). ~200 MB of broadly-useful utility. That would also make a hypothetical art target leaner, since it only adds the vector/3D/diagram tools on top. Separate conversation, but worth registering.

**Professions** `[ ]` (image layers — the highest-value gap, since these are pure Dockerfile + `tag.docker`, no launcher code):
- `[data]` — pandas / polars / duckdb / jupyter / csvkit. For data-pipeline and analysis work.
- `[infra]` — terraform / kubectl / helm / ansible baked in. For infra / devops agents. (Distinct from the optional-creds path, which only mounts *credentials* — this bakes the *tools*.)
- `[media]` — ffmpeg / imagemagick / yt-dlp, for media / download agents.
- `[docs]` — pandoc / LaTeX / mermaid-cli, for doc-heavy agents.

**Policies** `< >` (settings fragments — cheap, no image cost):
- `<-rm>` (deny) — block destructive shell: `Bash(rm -rf *)`, `Bash(git clean *)`, etc. A guardrail short of full `{frozen}`.
- `<-secrets>` (deny) — `Read` denies on `**/.env`, `**/.aws/**`, `**/credentials*` — keep an agent's eyes off secret files.
- `<!edits>` (obligation) — `defaultMode: acceptEdits`: auto-accept file edits but still prompt for bash. The natural middle rung between normal and `{auto}`.
- `<+read>` (allow) — allow all `Read`/`Glob`/`Grep` without prompts; a milder autonomy than `<+bash>`.

**Specialties** `{ }`:
- `{persist-home}` — bind-mount a host dir at `~/.local` so tools an agent installs survive across launches. Feasible today via `tag.docker` `[run] mounts`.
- `{scratch}` — mount a big host scratch dir at `/scratch` for large intermediates. Also just a `tag.docker` mount.
- `{gpu}` (`--gpus all`) and `{net-host}` (`--network=host` at run) — genuinely useful for ML / local-server-testing agents, **but they need a `tag.docker` extension**: `[run]` currently models `cap_add`/`entrypoint`/`mounts`/`env_forward`, not arbitrary `docker run` flags. Adding a small `run_flags` list (or named `gpus`/`network` fields) is the extension point — ~an afternoon, and then both become pure data.

**Engines** `( )` (conf variations only):
- `(draft)` — sonnet/haiku at low effort, thinking off: fast cheap iteration, a rung below `(poet)`.
- `(delegator)` — sets `CLAUDE_CODE_SUBAGENT_MODEL` to a cheap model so an agent that fans out many subagents keeps them inexpensive while the main loop stays premium.





switch between agents mid-session
=================================
It's possible to switch between agents mid-session, but only if they have the same settings (in .conf files), specifically same workspace.

Claude Code supports custom commands in .claude/commands/. You could create a /switch command that overwrites the active CLAUDE.md with a different agent's instructions. Claude Code re-reads CLAUDE.md as context refreshes, so the new
persona would take effect.

1. Mount the agents/ directory into the container (it's not currently mounted).
2. Create a command file like .claude/commands/switch.md that instructs Claude to:
- List available .md files in the mounted agents dir
- Ask which one to switch to
- Overwrite the active CLAUDE.md with that agent's content

Such a feature wasn't developed because the conf limitation is too big.




Extra agent features (through extra agent files)
====================
Custom slash commands (.claude/commands/*.md) — Give each agent its own toolkit of commands. A reviewer agent gets /checklist, a researcher gets /deep-dive, etc. These are just markdown prompt templates.

MCP servers (.claude/settings.json → mcpServers) — This is the big one. You can give agents access to entirely different tools: a database agent gets a Postgres MCP server, a researcher gets a web-search MCP, a DevOps agent gets a
Kubernetes MCP. This fundamentally changes what the agent can do, not just how it thinks.

Hooks (settings.json → hooks) — Shell commands that fire before/after tool calls. One agent could auto-lint after every edit, another could block destructive bash commands, another could log all file changes for audit.

Tool permissions (settings.json → allow/deny) — Restrict what tools an agent can use. A read-only reviewer agent could be denied Write, Edit, and Bash. A dangerous "yolo" agent could have everything allowed.

.claudeignore — Control what files each agent can see. A frontend agent ignores backend code, a security agent sees everything.

communications between agents (on same PC; maybe commonly mounted file?)
    agents talking to each other, such as front-end and back-end; going back and forth to resolve issues

  Can local AIs communicate? Yes. Each agent runs in its own container with shared filesystem mounts, so a "messages/" directory in the workspace is the simplest message bus — agent A writes a turn, agent B reads it, replies into the same
   file. No network needed.

  Can they prompt each other? Yes, two ways:
  - Subprocess (cleanest): Claude Code has a non-interactive -p mode. From inside one agent's container, you can run claude -p --append-system-prompt "$(cat /agents/worker.md)" "<the prompt>" via the Bash tool, capture stdout, and feed
  the response back to the caller. Stateless one-shot, perfect for manager → worker delegation.
  - Persistent two-way (more work): each agent runs in its own long-running container with a shared transcript file. An external coordinator (or a "turn token" file) decides whose turn it is. Each agent's CLAUDE.md instructs it to read
  prior turns and append its own. Better for debates and back-and-forth.

  Can confirmations work? Yes — three layers:
  - Claude Code's built-in permission system still applies, so risky actions (Bash, Write, Edit) prompt the user inside whichever agent's session is active.
  - For unattended runs, --dangerously-skip-permissions + a tight --allowedTools whitelist (the worker only gets read tools, say) is the standard pattern. Anthropic's init-firewall.sh (already on your TODO) is what makes that safe.
  - For "manager wants worker's work confirmed by human": the manager's session shows the worker's output and the manager waits for your approval before proceeding. Just one human-in-the-loop point.

  For starting with just two, I'd start with the subprocess pattern. Concrete shape:

  1. Mount agents/ into the container (currently it isn't).
  2. Add a custom skill, e.g. /delegate <name> "<prompt>", that runs claude -p --append-system-prompt "$(cat agents/<name>.md)" "<prompt>" and returns the output.
  3. The manager agent's CLAUDE.md describes when to use /delegate, what to send, how to act on the response.
  4. Optionally, a second /converse <name> skill that maintains a /conversation/<thread>.md file for multi-turn back-and-forth.

  That's a couple-hours add and gives you manager+worker, philosopher+philosopher, etc. The Claude Agent SDK is the heavier alternative if you ever want full programmatic control of the loop, but subprocess fits this launcher's grain.

/unspagghetify:
    High level: SEPARATE stuff. Categorizing different sections of the program naturally helps box problems into smaller scopes (making the "untangling" process much easier)
        - Make the program LOOK the way it runs. The file-structure should reflect the behavior
        -- Comprehensive sets of files; if you have an enum for some data, make sure that similar data would get its enum too, so that readers would get a clear picture of the code from observing base-structures (looks the way it runs)
        -- Make the functions general and the code dynamic, so expansion would be easy ; unless the program is super-specific (looks the way it runs)
        - When something gets over-complicated, consider offloading some responsibilities to the utility modules

/refactor:
    make functions be more "honest":
        - don't ask for more than necessary (if an arg is just "iterable", don't ask for a list ; if the order doesn't matter, ask for a "collection"...)
        - concise args: if you need 2 fields from 2 objects for a total of 4 args, go all the way in one direction rather than remain ambiguous :
        -- Option 1: you may as well just receive the 2 objects in full
        -- Option 2: run as a math/util function that's blind to the existance of such objects, and only cares about those values
        - does the function name make sense? 
        - does it make sense that the function returns its specific types? ('yes' if they're produced during the function's run)
        -- can the function return just one item and have the other items inferred from the returned one? Return more than one item if they're *complementary*, not derivative
        - does the function compute/fetch something that gets recomputed/refetched by following function calls? If so, consider passing the computing/fetching as an arg, outside the function, for the sake of efficiency (depends on your code layout...)
    add functions:
        Every "if" is a potential function. It defines a split in the code.
        Whenever you add a function, check if it can be reused in other places within your code.
    function-definition considerations (not hard rules):
        - single-responsibility principle (Uncle Bob)
        - seperate functions for producing data / acting on it (Tony Van Eerd)
        - no raw loops: loops with non-trivial bodies should be pulled into their own functions or expressed through generic algorithms (Sean Parent)
    Conceptually, what parts of the program could run in parallel? (think about the code as tasks, and consider which are required at the same time and have no overlap/co-dependencies)
        If the program NEEDS to be fast, consider building up your data as lists of fields rather than a list of object-with-fields to support SIMD
