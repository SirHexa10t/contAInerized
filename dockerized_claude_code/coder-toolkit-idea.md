You corrected me on two things and you're right on both — let me own that and rebuild from there.

**On "narrow value":** conceded. Once you factor in the weekly `SOFTWARE_STACK_REFRESH` re-pull (rustup/node/uv reinstall on the cache-buster rotation) and per-build time, not just disk, the cost of carrying unused tools is recurring, not one-time. And size hints in the form make "all of them" an informed choice rather than a shrug. So offering the full set is the right call, not scope creep.

**On global-vs-per-instance:** you're right, I over-applied the per-instance lens. `[code]` resolves to a single shared `claude-agents:code` image that's built once and reused by every `[code]` instance — that's the deliberate design, and the shared toolchain caches (`~/.claude-agents/cache/`) reinforce it: one Rust install, one cargo registry, amortized across all instances. So a global toolkit config isn't fighting the model — it's configuring the one shared artifact, which is exactly coherent. "Edit the profile → the shared image rebuilds once → all instances get it next launch" is correct, **with one mechanical requirement**: the selections must reach the build as `--build-arg`s (not, say, a file read at container runtime), so Docker's layer cache busts when you change them. Good news — that plumbing already exists: `[code]`'s `tag.docker` already declares `arg_forward = ["INSTALL_*", ...]`, and the launcher already computes `INSTALL_<TOOL>` flags today (just from creds-presence). So this is *extending* an existing gate, not building a new subsystem.

So: the idea is more viable than I first credited. Here's what genuinely remains to get right.

**1. The one real gotcha left — image identity.** `claude-agents:code` no longer fully describes its own contents (two machines with different profiles produce different images under the same tag). On a single machine that's harmless. It only bites if you ever inspect/share/debug images ("why is cmake missing from my code image?") — the answer lives in a separate file, not the tag. Minor; just worth a note in the profile's header comment.

**2. The default can't be a naive "all on."** `gcloud` alone is ~400–500MB. If the generated profile defaults everything selected, every fresh user eats half a gig of cloud CLIs they may never touch — a real regression from today, where cred-gating means no creds ⇒ not installed. So the sensible default is split: **core toolchains on (cmake, Rust, Node), heavy/niche CLIs off** (or defaulted to "on iff creds present"). This is the one place I'd push back on "all selected."

**3. Your "installed but dormant" idea is clean — here's the precise framing.** There's nothing to actively make dormant: a CLI installed without its config/creds is *already* inert — it just errors helpfully if invoked without auth, and the launcher never calls it (the agent does). So "dormant" = "present on PATH, unconfigured," costing only space+build-time. That lets you cleanly **decouple the two axes** the current design conflates: the *profile* decides "is the binary in the image," and *creds presence* decides "is it configured/usable." A tool can be installed-and-idle, or installed-and-authed. That's strictly better than today's single creds-drives-install gate — and it lets you retire that coupling (creds go back to only mounting config). The catch is just #2: don't let "decoupled + default-on" quietly install the 500MB ones for everyone.

**4. Your Dockerfile question — yes, and you already have the pattern.** "One Dockerfile that installs each tool on the condition the environment specifies it" is exactly the optional-cred section today: `ARG INSTALL_GH=0` + `RUN … if [ "$INSTALL_GH" = "1" ]`. Generalize that shape to *every* toggleable tool (Rust, Node, cmake each become an `ARG INSTALL_<X>` + gated RUN). That resolves most of the drift worry — the Dockerfile is the install mechanism for all of them, uniformly.

The residual drift is: the *launcher* also needs to know the tool list (to generate the default profile, render the form, show sizes) — and that can't come from the install RUN blocks. So the clean source-of-truth is a small **repo-side manifest** (e.g. `agents/profession/code/toolkit.toml`): one entry per tool with `name`, one-line description, size hint, and default. The launcher reads it for the profile/form/build-args; the Dockerfile keeps its gated RUN blocks; and a coverage test asserts the manifest's tool set exactly matches the Dockerfile's `INSTALL_*` ARGs (we already parse those ARGs in `test_env_coverage` — it's a natural extension). Add a tool → touch manifest + Dockerfile, test enforces both. That also makes it a *general* "a profession may expose a configurable toolkit" capability rather than a `[code]` one-off, which answers my earlier "doesn't generalize" worry.

**5. Minor: cache-layer ordering.** Toggling an early RUN busts everything downstream. The Dockerfile already orders stable-before-optional for this reason; with everything toggleable it matters a bit more, but toolchain toggles are rare, so it's a non-issue in practice — just don't put a frequently-toggled tool first.

So the shape I'd land on: **repo manifest (source of truth: tools + sizes + defaults) → generated global `~/.claude-agents/coder_profile.toml` (comments carry the size hints) → picker form editing it (your `checkbox_form`, top-level entry above delete) → `INSTALL_*` build args (existing `arg_forward` plumbing) → uniformly-gated Dockerfile**, with creds decoupled to config-only and heavy CLIs defaulting off. Less new machinery than my first reply implied — mostly a manifest, a profile reader/generator, and extending the flag computation you already have.

Two decisions that shape it before any build:
- **Default for the heavy cloud CLIs** — off, or "on iff creds present"? (I'd avoid default-on.)
- **Do you want to fully retire the creds→install coupling** (profile owns install, creds own config), or keep creds as an *additional* auto-include on top of the profile? The first is cleaner; the second is more backward-compatible.
